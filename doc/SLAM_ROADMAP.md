# SLAM Roadmap: карта и отображение в Android

Цель: реализовать полный контур SLAM для `xiaomi_robot`:
1) запись своего лога движения в intel-подобном формате,
2) построение карты алгоритмом RBPF-SLAM (сначала Python прототип),
3) отображение карты в Android-приложении в реальном времени.

---

## 1. Этап A: запись лога через Android-джойстик

### 1.1 Что делаем

- Управляем роботом вручную из Android (джойстик `cmd_vel`).
- На роботе `log_node` пишет сессию в файл формата, совместимого с Intel/CARMEN.
- На выходе получаем воспроизводимый лог для оффлайн SLAM.

### 1.2 Минимальный формат лог-файла (intel-like)

Используем CARMEN-подобные строки:
- `ODOM x y theta tv rv accel ipc_timestamp host logger_timestamp`
- `FLASER N r1 r2 ... rN x y theta odom_x odom_y odom_theta ipc_timestamp host logger_timestamp`

Комментарии в начале файла:
- `# message_name [message contents] ipc_timestamp ipc_hostname logger_timestamp`
- `# message formats defined: PARAM ODOM FLASER`

Рекомендуемая частота:
- `ODOM`: 10-20 Hz
- `FLASER`: как приходит лидар (обычно 5-10 Hz)

### 1.3 Изменения в проекте

- `cpp/app/src/nodes/log_node.cpp`
  - подписка на `types::OdometryData`
  - подписка на лазерный топик (скан в порядке "слева-направо" или как в driver, но консистентно)
  - синхронизация `odom` + `laser` по ближайшему времени
  - writer в файл `*.log` (ротация по сессии)
- Добавить CLI/конфиг:
  - путь файла лога
  - старт/стоп записи
  - флаг flush/буфер

### 1.4 Критерии готовности

- Лог открывается парсером CARMEN без ошибок.
- В логе есть и `ODOM`, и `FLASER`, а timestamp монотонны.
- На 5-10 минут ручного проезда лог не поврежден и не теряет структуру.

## 2. Этап B: RBPF-SLAM на Python (прототип)

### 2.1 Что делаем

- Реализуем отдельный Python-пайплайн:
  - читает лог формата Intel/CARMEN,
  - запускает RBPF (particle filter + occupancy grid),
  - строит карту и траекторию.
- Это референс поведения перед переносом в C++ `slam_node`.

### 2.2 Структура прототипа (предложение)

- `tools/slam_rbpf/`
  - `parser.py` — чтение `ODOM/FLASER`
  - `motion_model.py` — модель движения
  - `sensor_model.py` — likelihood поля/beam model
  - `rbpf.py` — частицы, веса, resampling
  - `grid_map.py` — occupancy update (log-odds)
  - `run.py` — запуск и сохранение результата

Выход:
- `map.pgm`/`map.png`
- `trajectory.csv`
- опционально `debug.json` (ESS, ресемплинг, параметры)

### 2.3 Базовые параметры (стартовые)

- Частицы: 30-80
- Размер ячейки: 0.05 м
- Дальность: по lidar max usable range
- Resample: по ESS (например < 0.5 * N)

### 2.4 Критерии готовности

- На `intel.log` и на своем логе строится осмысленная карта.
- Карта воспроизводится при повторном запуске с фиксированным seed.
- Время обработки сессии приемлемо для оффлайн анализа.

## 3. Этап C: перенос в C++ и `slam_node`

### 3.1 Что делаем

- Переносим отлаженный pipeline в `cpp/app/src/nodes/slam_node.cpp`.
- `slam_node` подписывается на `odometry_data` и `laser_data`.
- Публикует:
  - текущую позу,
  - состояние карты (полный снэпшот и/или дельта-обновления).

### 3.2 Интерфейсы сообщений (черновик)

- `types::SlamPose { timestamp, x, y, yaw }`
- `types::MapMeta { width, height, resolution, origin_x, origin_y }`
- `types::MapTile` или `types::OccupancyGrid` (0..100 / -1 unknown)

### 3.3 Критерии готовности

- C++ версия строит карту, сопоставимую с Python baseline.
- CPU/RAM на роботе в пределах бюджета (без деградации базового управления).
- Нода стабильно работает на длительной сессии.

## 4. Этап D: визуализация карты в Android

### 4.1 Что делаем

- Добавляем экран карты в Android-приложение:
  - viewport (pan/zoom),
  - робот (поза + heading),
  - обновление карты в реальном времени.
- Организуем канал передачи данных "робот -> телефон" по сокету.

### 4.2 Транспорт (предложение)

- На роботе: TCP/WebSocket сервер (лучше WebSocket для Android-клиента).
- Протокол сообщений:
  - `map_meta`
  - `map_chunk`/`map_delta`
  - `pose`
  - `status`/`heartbeat`

Формат:
- JSON для метаданных и управления.
- Бинарный payload для карты (сжатие zlib/lz4) для экономии трафика.

### 4.3 Android UI

- Новый экран `MapScreen`:
  - canvas/OpenGL рендер occupancy grid,
  - слой траектории,
  - слой текущей позы.
- Индикаторы:
  - connected/disconnected,
  - задержка, частота обновлений.

### 4.4 Критерии готовности

- Карта и поза видны в приложении в реальном времени.
- Потеря сети обрабатывается без падения приложения.
- Повторное подключение восстанавливает отображение состояния.

## 5. Этап E: движение в точку (Tap-to-Go) из Android

### 5.1 Что делаем

- Пользователь выбирает точку на карте в Android (`tap`).
- Приложение отправляет `nav_goal` на робота.
- На роботе `navigation_node` строит путь и ведет робота к цели.

### 5.2 Контракт сообщений и координаты

- Добавить тип цели:
  - `types::NavGoal { timestamp, frame_id, x, y, yaw(optional), pos_tolerance }`
- Зафиксировать системы координат:
  - `map` (глобальная карта),
  - `base_link` (робот),
  - `screen` (пиксели UI).
- Реализовать преобразование:
  - `screen tap -> map (x,y)` в Android,
  - валидация: цель в пределах карты и не в занятой ячейке.

### 5.3 Планирование пути (global planner)

- Версия v1: `A*` по occupancy grid.
- Costmap с инфляцией препятствий:
  - учитывать радиус робота + safety margin.
- Результат:
  - `planned_path` (список waypoint),
  - статус `unreachable`, если путь не найден.

### 5.4 Локальное ведение и безопасность

- Контроллер v1: `Pure Pursuit` (или эквивалентный трекер траектории).
- Генерация `cmd_vel` с ограничениями:
  - `v_max`, `w_max`, accel/decel.
- Защита:
  - emergency stop при близком препятствии,
  - replan при блокировке пути,
  - timeout для незавершенной цели.

### 5.5 Архитектура на роботе

- Новая нода: `cpp/app/src/nodes/navigation_node.cpp`.
- Подписки:
  - `slam_pose`, `occupancy_grid` (или map tiles), `nav_goal`, obstacle feed.
- Публикации:
  - `cmd_vel`, `nav_status`, `planned_path`.
- Состояния:
  - `IDLE -> PLANNING -> TRACKING -> REPLANNING -> REACHED/FAILED/CANCELED`.
- Приоритет ручного режима:
  - вход от джойстика должен прерывать автодвижение (`manual override`).

### 5.6 Android UI для цели

- На `MapScreen`:
  - тап по карте = маркер цели,
  - кнопки `Go` / `Cancel`.
- Отображать:
  - текущий путь,
  - статус (`Planning`, `Moving`, `Blocked`, `Reached`, `Failed`),
  - текущую позу робота.

### 5.7 Критерии готовности

- Робот стабильно доезжает до выбранной точки в типовых сценариях.
- Недостижимая цель корректно отклоняется с понятным статусом.
- Отмена цели и manual override работают без зависаний.
- Путь и статус корректно видны в Android в реальном времени.

## 6. Этап F: алгоритм уборки (explore + map + coverage)

Цель этапа: робот должен одновременно исследовать неизвестное пространство, уточнять карту и
выполнять покрытие всей доступной площади траекторией уборки.

### 6.1 Поведение верхнего уровня (mission manager)

- Добавить `cleaning_node` (или `mission_node`) с режимами:
  - `EXPLORE` — исследование неизвестных областей,
  - `COVERAGE` — систематическая уборка известных свободных зон,
  - `RETURN_HOME` — возврат на базу/старт по завершению.
- Переключение режимов по условиям:
  - нет достижимых frontier -> перейти в coverage,
  - покрытие завершено -> return home.

### 6.2 Исследование пространства (exploration)

- Выделять frontier на occupancy grid:
  - frontier = граница между `free` и `unknown`.
- Выбирать цель исследования:
  - nearest frontier / utility score (информация + расстояние + риск).
- Использовать уже готовый стек навигации этапа E:
  - отправка `nav_goal`,
  - контроль статуса и replan.

### 6.3 Покрытие всей свободной области (coverage path planning)

- После стабилизации карты строить покрывающую траекторию:
  - вариант v1: boustrophedon/lawnmower по свободным ячейкам,
  - с учетом ширины зоны уборки (диаметр щетки/корпуса + overlap).
- Ограничения:
  - инфляция препятствий и запрет на узкие не проходимые коридоры.
- Контроль покрытия:
  - mask "visited free cells",
  - повторное планирование непокрытых островков.

### 6.4 Согласование SLAM и уборки

- В процессе движения карта продолжает обновляться.
- При сильных изменениях карты:
  - перепланирование траектории уборки,
  - локальная коррекция без полного сброса миссии.
- Устойчивость к сбоям:
  - временная потеря локализации -> safe stop + recovery.

### 6.5 Критерии завершения уборки

- Уборка считается завершенной, когда:
  - покрыто >= X% доступной свободной площади (например 95%),
  - оставшиеся непокрытые зоны недостижимы/меньше порога площади.
- Формировать отчет сессии:
  - площадь уборки, длительность, путь, число replan, причины пропусков.

### 6.6 Android UI для режима уборки

- Добавить экран/блок `Cleaning Mission`:
  - кнопки `Start Cleaning`, `Pause`, `Resume`, `Stop`, `Return Home`.
- Показ в реальном времени:
  - текущий режим (`Explore`, `Coverage`, `Return`),
  - процент покрытия,
  - карта "убрано/не убрано",
  - диагностические статусы (`blocked`, `replanning`, `recovering`).

### 6.7 Критерии готовности

- Робот выполняет автономную уборку неизвестного помещения без ручного задания точек.
- Карта строится и уточняется в процессе движения.
- Достигается целевой coverage KPI (например >=95% на тестовом полигоне).
- Поведение устойчиво к типовым препятствиям и временным блокировкам.

## 8. Риски и меры

- Разъезд odom и lidar timestamp:
  - ввести буфер и nearest-neighbor sync по времени.
- Нагрузка на CPU робота:
  - начать с меньшего числа частиц + профилирование.
- Большой трафик карты:
  - передавать дельты/тайлы и компрессию.
- Дребезг качества карты из-за ручного вождения:
  - чеклист записи (скорость, петли, проходы вдоль стен).
- Неполное покрытие из-за шума карты/локализации:
  - хранить coverage mask, повторно обходить "островки", пороги на мелкие зоны.
- Зацикливание между explore и coverage:
  - добавить hysteresis и лимиты на число перепереходов режимов.
