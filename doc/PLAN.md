# План проекта: собственная логика уборки для Xiaomi Mi Robot Vacuum (1st gen)

**Модель:** `rockrobo.vacuum.v1`, кодовое имя **ruby** (OEM Roborock).

Цель: довести решение до уровня «как в проде» для аналогичных роботов-пылесосов: робот выполняет **полноценную автономную уборку**, а пользователь управляет ею из **Android-приложения** (карта, кнопки старт/пауза/стоп/домой, статус и логи).

Техническая часть: приложение на **C++**, собираемое на ПК, с выкладкой **бинарника на робота по SSH**. Функции на роботе: **карта**, **маршрут**, **скорости колёс**, **лидар и остальные сенсоры**.

Связанные документы: [BURN.md](./BURN.md) — прошивка с SSH/Valetudo и **оперативный чеклист** сценария bring-up (§«Сценарий подготовки к работе с Player»); [SYSTEM_DESIGN.md](./SYSTEM_DESIGN.md) — архитектура компонентов и потоков данных (в т.ч. **штатный стек Player** в §4.1); публичные материалы по железу и прошивкам — ссылки в [§14](#14-источники-и-материалы-для-углубления).

## 2. Предпосылки, риски, безопасность

- **Root и стабильная кастомная прошивка** (например через DustBuilder / [zvldz/vacuum](https://github.com/zvldz/vacuum)) с **SSH** — без этого смысла в «одном бинарнике» мало.
- Рекомендации сообщества по линейке прошивок gen1: ориентироваться на проверенные **v11_…** пакеты и документацию Valetudo/Dustcloud для своей ревизии; часть прошивок **усложняла root/прошивку** — иметь запасной образ и процедуру отката (см. обсуждения в [dustcloud](https://github.com/dgiese/dustcloud)).
- **Эксклюзивный доступ к UART:** пока работает штатный `player`, порты `ttyS1/ttyS2` заняты. Поэтому есть два режима: (1) direct UART с остановкой стека; (2) стандартный доступ через Player API без захвата UART своим процессом (см. §4).
- **Безопасность:** первые прогоны — подставка / колёса в воздухе, лимиты скорости, **watchdog** (аппаратный по питанию моторов или таймер в коде), немедленный стоп по cliff/bumper.

## 2.1. Продуктовый scope (MVP и прод-уровень)

**MVP (обязательный минимум):**

- Старт уборки из Android (кнопка `Start`) и остановка (`Pause/Stop`).
- Отображение текущей позы робота и упрощённой карты в реальном времени.
- Полный цикл уборки комнаты без ручного вмешательства.

**Прод-уровень (цель проекта):**

- Стабильная покрывающая уборка с восстановлением после типовых ошибок (застревание, bump, потеря скана).
- Режимы уборки (полная/зональная), возврат на базу, сохранение истории и логов сессий.
- Устойчивый мобильный UX: прогнозируемая задержка обновлений карты и статуса, корректная обработка потери сети.

## 3. Фаза A — инвентаризация на живом роботе (1–3 дня)

Конкретный чек-лист:

1. **Версия и диск:** `uname -a`, `cat /etc/os-release` (если есть), `df -h`, `free`.
2. **libc для кросс-компиляции:** `ldd --version` на роботе; зафиксировать путь к динамическому линкеру (`readelf -l` на любом бинарнике).
3. **UART:** `ls -l /dev/ttyS*`; при работающей уборке — `lsof | grep ttyS` или `fuser -v /dev/ttyS*` (что реально открыто).
4. **Процессы:** `ps` / `top` в простое и во время уборки; имена процессов, которые нужно гасить для теста.
5. **Утилиты:** есть ли **`uart_test`** и с какими ключами читаются «сырые» данные MCU (зависит от образа).
6. **Лидар:** снять короткий дамп с предполагаемого порта (`dd`/`cat` с осторожностью или маленькая C++ утилита на `termios`) и сверить с описанием пакетов **Delta‑2D** (см. [codetiger/VacuumRobot lidar-reader README](https://github.com/codetiger/VacuumRobot/blob/main/Research/Software/Firmware/lidar-reader/README.md)).

**Выход фазы:** таблица «ресурс → `/dev` или сокет → кто держит → формат данных / что известно из RE».

### 3.1. Результаты инвентаризации (снято по SSH, апрель 2026)

Снимок с рабочего робота в домашней сети (адрес в лаборатории меняется; ниже — факты с железа).

| Ресурс | Значение |
|--------|----------|
| Хост / ядро | `Linux rockrobo 3.4.39 #1 SMP PREEMPT Sat Jan 9 09:34:52 UTC 2021`, **armv7l** |
| Дистрибутив | **Ubuntu 14.04.3 LTS** (Trusty) |
| Версия образа Roborock | **`ROCKROBO_VERSION=3.5.8_004028`** (`/etc/os-release`) |
| libc (кросс-компиляция) | **EGLIBC 2.19** (`ldd (Ubuntu EGLIBC 2.19-0ubuntu6.6) 2.19`) |
| RAM | ~**500 MiB** всего, **swap отсутствует** |
| `/` | **~494 MiB** (`/dev/root`), занято ~57% |
| Данные | **`/mnt/data`** на `mmcblk0p1`, **~1.6 GiB** |
| Утилита `readelf` | на устройстве **нет** — интерпретатор для бинарников смотреть кросс-`readelf` на ПК |

**Таблица UART (простой, без уборки):**

| Устройство | Группа / права | Кто держит (по `lsof`) | Заметка |
|------------|------------------|-------------------------|---------|
| `/dev/ttyS0` | `root:tty` | `getty` 115200 | последовательная консоль |
| `/dev/ttyS1` | `root:dialout` | **`player` (PID 826)** | по литературе — типичный кандидат под **лидар**; подтвердить дампом при остановленном `player` |
| `/dev/ttyS2` | `root:dialout` | **`player`**, fd **заблокирован на запись** (`60uW`) | типичный кандидат под **MCU**; `uart_test` при работающем `player` пишет *«/dev/ttyS2 already locked»* |

**Ключевые процессы (штатный стек + Valetudo):**

| Процесс | Назначение (ориентир) |
|---------|------------------------|
| `player /opt/rockrobo/cleaner/conf/ruby_chassis.cfg` | навигация / chassis, **владелец ttyS1/ttyS2** |
| `miio_client`, `AppProxy`, `miio_client_helper_nomqtt.sh`, `miio_recv_line` | облако / miIO |
| `/usr/local/bin/valetudo` | локальный веб/управление |
| `WatchDoge /opt/rockrobo/watchdog` | watchdog |
| `RoboController`, `wlanmgr`, `wpa_supplicant` / `dhclient` на `wlan0` | низкоуровневое управление и Wi‑Fi клиент |

**Сеть (лабораторный снимок):** `wlan0` — клиент в домашней сети; **`wlan1`** есть, **DOWN**. В образе присутствуют **`/usr/sbin/hostapd`** и **`/usr/sbin/dnsmasq`** (для AP/раздачи — отдельная настройка, см. §11).

**Утилита `/usr/bin/uart_test`:** есть; при запущенном `player` не получает эксклюзивный доступ к `ttyS2`. Для снятия сырых логов — остановка конфликтующих процессов (§4) или перехват.

**Статус фазы A:** инвентаризация **выполнена** для версии **3.5.8_004028**; остаётся **опционально** повторить `lsof`/ `ps` **во время штатной уборки** и сделать **короткий дамп лидара** с `ttyS1` после контролируемой остановки `player` (перед фазой B).

### 3.2. Штатный стек `/opt/rockrobo/cleaner` (Player)

На **rockrobo** навигация и уборка в прошивке завязаны на **Player** (middleware): процесс **`player`** читает **`/opt/rockrobo/cleaner/conf/ruby_chassis.cfg`** и поднимает цепочку **драйверов** как динамические библиотеки из **`/opt/rockrobo/cleaner/lib/`**. Каталог компактный (порядка **40+** файлов): `bin/`, `conf/`, `lib/`, `misc/`.

**Состав `bin/` (ориентир):**

| Файл | Роль |
|------|------|
| **`player`** | ELF **ARM 32-bit**, линкуется с `libplayercore.so`, `libplayerdrivers.so`, … — ядро Player |
| `AppProxy`, `RoboController`, `RoboControllerM`, `SysUpdate` | Вспомогательные бинарники экосистемы (не все обязаны быть «рядом» с одним процессом) |

**Граф драйверов в `ruby_chassis.cfg` (логика, не полный текст):**

| Имя в cfg | Плагин (`.so`) | Смысл |
|-----------|-----------------|--------|
| `ruby_compass` | `librubycompassdriver` | Компас → `position3d` |
| `ruby_chassis` | `libchassisdriver` | **Шасси / MCU:** одометрия, бампер, ИК, сонар, моторы щёток, heart-beat к MCU и т.д. |
| `ruby_laser` | `librubylaserdriver` | **Лидар:** в конфиге **`port "/dev/ttyS1"`**, выходы `raw` / `nav` / `slam` |
| `rrslam` | `librrslamdrv` | SLAM и карта; пути вроде **`/mnt/data/rockrobo/last_map`**, тестовая карта в **`misc/mobility_test_map`** |
| `DriverTest` | `libNavDriver` | Высокоуровневый нав. драйвер, `provides control:::aio:0`, тянет сенсоры + карту + SLAM |
| `writelog`, `ruby_support` | — / `librubysupport` | Логирование |

**Связь с UART (согласование с §3.1):** в cfg **явно** указан только **`ttyS1`** для лазера; процесс **`player`** на снимке держит **и `ttyS1`, и `ttyS2`** (`ttyS2` с блокировкой записи — разумный кандидат на **протокол Linux ↔ STM32** через `libchassisdriver` / `libuart_api.so`).

**Практика для своего кода:** остановка **`player`** (и при необходимости **`WatchDoge`**) освобождает порты; готовые скрипты — [`app/scripts/stop_player.sh`](../app/scripts/stop_player.sh) и [`start_player.sh`](../app/scripts/start_player.sh). Чтение лидара без Player — [`app/lidar_reader`](../app/README.md).

Подробнее в контексте целевой архитектуры — [SYSTEM_DESIGN.md §4.1](./SYSTEM_DESIGN.md#41-штатное-по-до-замены-player-в-optrockrobocleaner).

## 4. Фаза B — минимальный PoC и выбор режима доступа к сенсорам

1. Остановить конфликтующие сервисы (конкретные команды зависят от образа; ориентир — процессы `miio` / `player` / навигационные демоны). После теста — понять, как поднимать сеть/SSH без полного factory набора.
2. Реализовать **тонкий C++ reader** лидара: `termios` 115200 8N1, разбор кадров по известному заголовку/CRC (портировать логику из открытых описаний протокола в свой код).
3. Опционально: **GPIO питание мотора лидара** (в RE фигурируют кандидаты вроде отдельного pin; подтвердить осциллографом/логикой или методичным перебором с осторожностью).

**Выход:** бинарник на роботе печатает в лог валидные дистанции/углы с Hz, достаточным для SLAM.

### 4.1. Статус интеграции Player-клиента (без ROS)

Сделан отдельный трек для работы **через штатный Player**, не занимая прямой UART к лидарам/MCU:

- единый интерфейс `IXiaomiPlayerClient` в `app/include/player_bridge.h`;
- две реализации в отдельных файлах:
  - `XiaomiPlayerClientC` (`app/src/player_client_c.cpp`, `libplayerc`, модель `xiaomi_bridge`);
  - `XiaomiPlayerClientCPP` (`app/src/player_client_cpp.cpp`, `libplayerc++`);
- фабрики в `app/src/player_bridge.cpp`:
  - `CreateXiaomiPlayerClientC(...)`
  - `CreateXiaomiPlayerClientCPP(...)`;
- `app/main.cpp` сейчас использует C-вариант по умолчанию.

Практический смысл: можно развивать телеметрию/управление через `player` без остановки `player`-стека и без отдельного решения по питанию LDS.

### 4.2. Стандартный режим через Player API (без `stop_player.sh`)

Вывод после сверки `3pp/player` и текущего плана: для задач **чтения сенсоров + управления** хак с остановкой штатного стека можно обойти, если работать как сетевой клиент Player.

Что это дает:

- `player` на роботе продолжает держать `ttyS1/ttyS2` и сам поднимает драйверы (`ruby_laser`, `ruby_chassis`, `rrslam`);
- наш процесс не лезет в UART напрямую, а читает данные через `libplayerc`/`libplayerc++`;
- запуск/питание LDS выполняет штатный драйвер `ruby_laser` как часть `player`-графа.

Ограничения:

- этот режим зависит от живого процесса `player` и корректного `ruby_chassis.cfg`;
- низкоуровневый протокол STM32 и «сырые» UART-кадры в этом режиме не видны;
- часть возможностей (тонкая диагностика MCU) все равно требует direct UART режима.

Рекомендованный порядок запуска сенсоров через Player API:

1. На роботе убедиться, что `player` запущен с `ruby_chassis.cfg`.
2. На клиенте создать `playerc_client` и подключиться (`host:6665`).
3. Создать нужные proxy (`laser`, `position2d`, `ir`, `sonar`, `power`).
4. Подписаться `*_subscribe(..., PLAYER_OPEN_MODE)`.
5. В цикле вызывать `playerc_client_read()` и читать поля proxy.
6. Для управления движением использовать `playerc_position2d_set_cmd_vel(...)`.

#### 4.2.1. Основной сценарий подготовки (зафиксирован как канон)

Для **отладки через штатный `player` на `6665`** (лидар + прокси + при необходимости `cmd_vel` / Valetudo manual) в проекте зафиксирован **один** практический сценарий «разогнать» стек и выйти в удобное для внешнего клиента состояние. Его **нельзя полностью автоматизировать** из-за **физических** шагов (кнопка, поднятие).

**Порядок (как в инструкциях community / bridge-гайд по Player):**

1. Убедиться, что **`RoboController` не** занимает сценарий (не запущен / не мешает).
2. По SSH (или в консоли робота) запустить **`/opt/rockrobo/cleaner/bin/RoboController`**.
3. **Нажать Home** на корпусе, чтобы робот **начал поиск дока / движение** (нужен реальный сценарий навигации, не простой idle).
4. Когда робот **устойчиво движется**, **остановить** `RoboController` (аналог `Ctrl-C` / `kill` с инт сигналом) — снять **верхний оркестратор** без аккуратного shutdown.
5. **Поднять робота** (сорвать с пола) — **прервать** навигацию и движение через **датчики** (cliff/поднятие/колёса), т.е. **аппаратный abort** движения, когда «мозг» навигации уже убит.
6. Ориентир готовности: **слышен только мотор лидара** (LDS крутится), дальше — проверка `player` на `127.0.0.1:6665` и запуск `xiaomi_robot` (см. [BURN.md](./BURN.md#сценарий-подготовки-к-работе-с-player-основной)).

**Смысл шагов (коротко):**

| Шаг | Зачем |
|-----|--------|
| `RoboController` | Поднять **высокоуровневый** путь: IPC к подсистемам, сценарии движения, согласование с MCU/логикой пылесоса. |
| Home + движение | Запустить **живой** навигационный сценарий, «разогнать» стек. |
| kill по `RoboController` | Выйти из оркестрации **вручную**; состояние может быть промежуточным. |
| Поднятие | **Сильный сигнал безопасности** остановить движение, когда сценарий уже **не** завершается штатно; часто остаётся **лидар + `player`**, удобные для **ручного/отладочного** управления. |

**Ограничения:** сценарий зависит от **образа** и **состояния** watchdog/процессов; при деградации стека сначала [health-check `player` в BURN.md](./BURN.md#health-check-player-перед-xiaomi_robot) и **iptables / порт 6665**.

Статус в репозитории:

- базовый путь уже реализован в `app/src/player_client_c.cpp`;
- по умолчанию `app/main.cpp` использует этот backend;
- это и есть основной путь для MVP без остановки штатного стека.

## 5. Фаза C — MCU: одометрия и привод

Здесь основной объём reverse engineering:

1. **Перехват:** пока штатное ПО крутит робота, записать сессию байтов на подозрительном `ttySx` (две стороны: Linux→STM32 и STM32→Linux).
2. **Корреляция:** сопоставить моменты старта/стопа колёс, удары бампера, срабатывание cliff с паттернами пакетов.
3. **Команды:** выделить кадры «задание скорости колёс» / «запрос одометрии»; воспроизвести минимальный набор в своём коде.
4. Альтернатива (тяжёлая): анализ бинарников (`strings`, Ghidra) с символами вроде `ttyS`, `RobotControl`, как в публичных разборах других моделей Roborock.

**Выход:** модуль `McUartTransport` + декодер статуса (бампер, cliff, одометрия) + кодер команд скорости с ограничителем.

## 6. Фаза D — тулчейн и деплой

1. **Кросс-компилятор** под **arm-linux-gnueabihf** с **glibc, совместимым с роботом**, или сборка в **chroot/sysroot**, снятом с устройства.
2. Если подобрать glibc сложно — **статическая линковка** (например **musl** `armv7-unknown-linux-musleabihf`) для одного исполняемого файла; проверить на роботе `ldd` = «not a dynamic executable».
3. **CMake**, C++17, флаги `-O2 -pipe`, опционально LTO после отладки.
4. Скрипт: `scp` + запуск; позже — **OpenRC/sysvinit** unit на Valetudo-образе (как принято в вашей прошивке).

## 7. Фаза E — HAL и симуляция на ПК

Интерфейсы (те же, что раньше, но с привязкой к реальности gen1):

| Модуль | Контракт |
|--------|----------|
| `LidarDriver` | полный оборот или пакеты → `LaserScan` (угол, дальность, time) |
| `McBridge` | байтовый протокол STM32 → одометрия, бампер, cliff; команды моторов |
| `MotionModel` | дифференциальная кинематика (два ведущих колеса + скольжение как параметр) |

Плюс **запись/воспроизведение логов** сессий с робота для регрессии без железа.

---

## 8. Фаза F — карта и локализация (алгоритмически)

- **Карта:** occupancy grid 5–10 см; лог-одд обновление по лучам лидара.
- **Поза:** одометрия из MCU + **scan-to-map matching** (корреляционная сетка или лёгкий ICP) для уменьшения дрейфа.
- **Ресурсы R16:** не тянуть тяжёлый 3D; достаточно 2D SLAM; частота лидара высокая — можно **прореживать** вход для CPU.

---

## 9. Фаза G — планирование и поведение

1. **Глобально:** покрытие зигзагом / Boustrophedon по свободным клеткам; разбиение комнат — после стабильной карты.
2. **Локально:** простой DWA или следование по глобальному графу с **отталкиванием** от динамических препятствий по лидару; при срабатывании бампера — короткий отъезд и обход.
3. **Приоритеты:** cliff > бампер > план.

---

## 10. Фаза H — интеграция и FSM

Состояния: `INIT` → `MAP_OR_CLEAN` → `RECOVER` → `SAFE_STOP` / `IDLE`.

Один главный цикл с измеряемой задержкой; логи с timestamp (`CLOCK_MONOTONIC`).

## 11. Точка доступа Wi‑Fi и сетевое взаимодействие

Цель: робот поднимает **свою Wi‑Fi сеть (AP)** или стабильно работает в известной топологии, чтобы с ноутбука/ПК **принимать и отправлять данные** без облака: телеметрия, отладка, потоковая карта.

**Задачи:**

1. **Инвентаризация (в фазе A):** какой интерфейс в AP-режиме на образе (`wlan0` и т.д.), есть ли **`hostapd`**, **`dnsmasq`** / `udhcpd`, **`iw` / `wpa_supplicant`**, поддержка **`nl80211`** у драйвера Realtek на ядре 3.4.
2. **Сценарии:**
   - **Режим «лабораторный AP»:** робот раздаёт Wi‑Fi (SSID/пароль в конфиге), на `br0` или `wlan0` — статический адрес (например `192.168.42.1`), DHCP для клиентов, маршрут не обязателен если достаточно локальной подсети.
   - **Режим «как сейчас»:** робот в домашней Wi‑Fi — тогда AP не нужен, но тот же транспорт телеметрии (§12) слушает на `0.0.0.0` или только на `wlan0`.
3. **Согласование с прошивкой:** у Valetudo/штатных образов уже бывает **режим provisioning AP**; зафиксировать, не конфликтует ли ваш `hostapd` со штатными скриптами, и в каком состоянии FSM робота поднимать свой AP (например только когда основной навигационный стек остановлен).
4. **Безопасность:** для полевых тестов — **WPA2-PSK**; не оставлять открытую сеть без необходимости.

**Выход:** скрипт или unit «поднять AP + DHCP»; проверка с ПК: `ping`, `nc`/ZMQ-порт с §12.

## 12. Телеметрия в реальном времени, визуализация и запись (ZeroMQ)

Цель: **в реальном времени** смотреть **карту**, **траекторию и план пути**, **логи**; **записывать** сессии для офлайн-разбора и регрессии; использовать эти же потоки как основу для Android UI.

**Почему ZeroMQ:** один процесс на роботе (C++) может **асинхронно публиковать** потоки без жёсткой связи с GUI; на ПК удобны подписчики на **Python** (matplotlib, PyQt, [rerun](https://rerun.io/), веб-сокет-мост) или второй C++ клиент; мало бойлерплейта по сравнению с сырым TCP, проще несколько каналов (мультипарт-сообщения / разные сокеты).

**Рекомендуемая схема:**

| Роль | Паттерн ZMQ | Содержимое |
|------|----------------|------------|
| Робот → ПК | **`PUB`** на `tcp://0.0.0.0:<порт>` | Кадры: лидара (подвыборка), поза \((x,y,\theta)\), обновления **occupancy grid** (дельты или редкие полные снимки), **текущий/запланированный путь**, строки **логов** (уровень + текст), диагностика FSM |
| ПК → Робот (опционально) | **`PULL`** на роботе + **`PUSH`** на ПК или **`REQ`/`REP`** | Команды «старт/стоп», смена режима, параметры планировщика без SSH |

**Формат сообщений:** единый **заголовок** (тип кадра, `monotonic_ns`, версия схемы) + полезная нагрузка; для простоты — **CBOR / msgpack / protobuf** (один раз описать `.proto` или схемы). Избегать неограниченного `PUB` полных карт каждый тик — слать **сжатые дельты** или уменьшенный превью-слой.

**Визуализация на ПК:**

- минимум: Python **`SUB`** + окно с **картой и полилинией пути** + панель логов;
- позже: экспорт в **MCAP/свой бинарный лог** для просмотра во внешних тулзах.

**Запись:**

- отдельный процесс **`telemetry_logger`** на ПК: подписан на те же топики, пишет **нарезку по времени** в файлы (сырой ZMQ не обязателен — лучше декодированные записи + опционально сырой дамп);
- на роботе дублировать **критичный лог** в **кольцевой файл** на flash при нехватке места — только при необходимости.

**Зависимости:** кросс-сборка **libzmq** для ARM (или статическая линковка с лицензионной проверкой); на ПК `pyzmq` / `cppzmq`.

**Выход:** стабильный поток 5–20 Гц для позы/пути и 1–10 Гц для превью карты без перегруза Wi‑Fi; воспроизводимый формат записи сессии.

**Примечание для Android:** обычно мобильное приложение подключают не к raw ZMQ напрямую, а через тонкий **API-шлюз** (WebSocket/HTTP) на роботе или на ПК-бридже, который конвертирует внутренние события в формат UI.
